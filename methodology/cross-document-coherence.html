1. The problem in one paragraph

The BOM token model is the canonical source of ~40 cited numbers that appear across: the validation brief (2026-05-18 HTML), the V4 BOM memo (2026-05-13 MD/PDF), several Notion brief rows, two L-shape Marimekko chart packs, an in-progress chart deck, and the model's own README + Z_Sources tab. When a single assumption changes — like the frontier-share trajectory moving from 30/40/50% to 7.5/6/5% on 2026-05-18 — every downstream artifact that cited the V4 number is silently stale. The current discipline ("model is source of truth") states the rule but provides no enforcement: nothing flags the brief that still cites the old number, nothing flags the chart deck that uses the old blended price, nothing flags the F-column source/note in the model that wasn't refreshed alongside the value. Drift accumulates invisibly until manual review catches it.

2. Terms (define-first-use)

  • SSOT — Single Source of Truth. One canonical place where a fact lives; everything else references it rather than copying.
  • Dependency graph — the directed-graph relationship between artifacts (model → brief → deck → email). If the model changes, every downstream node is potentially stale.
  • Dirty-flag — a marker indicating an artifact is out-of-date relative to its sources. Standard pattern in software build systems (Make, Bazel) and CI/CD pipelines.
  • Provenance — the recorded chain of "where did this number come from?" — typically a cell address, a source ID, a hash, or a URL.
  • Content addressing / hash — a fingerprint of a value (e.g., SHA-256 of "$9.00"). If the value changes, the hash changes. Lets you detect that "the $9 the brief cited" is not "the $9 the model now contains."
  • Hook (Claude Code) — a shell command triggered by a specific event (file edit, tool call, session start). Deterministic — not the agent's choice whether to run.
  • Skill (Claude Code) — a markdown instruction file the agent loads when relevant; encodes domain workflows.
  • MCP — Model Context Protocol; Anthropic's plug-in standard for external data sources and tools.
  • Subagent (Claude Code) — a separate context window dispatched for a focused task; returns a summary to the parent.
  • Quarto / docxtpl / python-pptx / Jinja2 — open-source render libraries that produce Word, PowerPoint, HTML, or PDF from templates plus data.
  • Macabacus / ThinkCell / UpSlide — commercial Excel→PowerPoint/Word link-maintenance add-ins commonly used at investment banks and PE shops.

For a single-user shop where the deliverables are mostly chart-and-table-embedded slides plus prose briefs, the natural fit is Macabacus single-seat — it links Excel named ranges (which the BOM model already uses) into both PPT and Word, with a one-click "Manage Links" refresh dialog. ThinkCell is PPT-only and misses Word entirely; UpSlide has more enterprise overhead than is useful at single-seat.

3.2 Software-architecture patterns

Independent of any finance tool, the established pattern is SSOT + explicit dependencies + dirty-flag:

  • Excel holds the canonical numbers (already true in the BOM model).
  • Every downstream artifact declares what it depends on (which named ranges, which model version).
  • A build system (Make, Snakemake, or a thin Python equivalent) detects when sources have changed and rebuilds dependents on demand.
  • For prose-plus-numeric deliverables, Quarto compiles a single source file (markdown prose + inline value lookups) into Word, HTML, PDF, or PowerPoint.

One-sentence summary from Thread 2: "Excel = source. Python orchestrator + Quarto = render. Makefile = stale-check." This is the dominant production architecture for automated finance reporting (Apryse Fluent, Vena, Omnidocs Create, Nemeth's 3-layer pattern). The cost is build effort, not subscription.

The catch for John's workflow: prose-heavy briefs flatten when forced into templates. A 2,500-word memo with embedded figures doesn't translate cleanly into {{ revenue_2030 }} placeholders. Quarto is great for tear sheets and comp tables; less great for narrative briefs.

3.3 AI-agent approaches

The newest finding, and the most consequential: no 2026 vendor ships cross-document coherence for finance Office-file graphs under AI-agent stewardship. Coding-agent tooling (Cursor, Aider, Devin) solves source-code coherence — but does not extend to the xlsx + docx + pptx + md + html graph that John actually produces. LangChain's 2026 enterprise report: more than 60% of agent production incidents are state-management failures — which is exactly this problem class.

What Claude Code already provides (~80% of the substrate per Thread 3):

  • Hooks — can fire on every xlsx write to re-hash cited numbers and stale-flag downstream artifacts
  • Skills — can encode the reconciliation discipline as citation-coherence-audit
  • Subagents — already used for the M1/M2/M3 pre-ship audit pattern
  • MCP servers — promising for file-change pub/sub but current implementations are mostly request/response
  • Auto-memory — wrong layer for per-packet provenance (it's for invariants)

What's missing (the 20% gap): a structured provenance.json manifest per model that maps every cited number to {id, value, model_cell, hash}, plus the hook that detects drift, plus the skill that runs reconciliation. Thread 3 estimates this as ~1 day of custom build on existing primitives.

4. The four options on the table

Option A — Custom Claude Code provenance layer

~1 day build Coverage: all AI-built artifacts Risk: custom maintenance

How it works: A provenance.json file sits next to each model. Every cited number has an entry like {"id": "frontier_share_2026", "value": 0.075, "model_cell": "Inputs!C25", "hash": "a3f9..."}. Briefs, slides, memos, and emails reference numbers by ID, not by raw value. A PostToolUse hook re-hashes on every xlsx write and stale-flags downstream artifacts whose referenced hashes no longer match. A coherence-audit skill + subagent runs the reconciliation pass on demand.

What it catches: Today's BOM episode — F-column source/note stale, brief number stale, README still saying "30%/40%/50%".

What it doesn't catch: Numbers John types into an Excel chart manually outside of Claude's edit path.

Option B — Macabacus + existing discipline

~$200-360/yr Coverage: Excel → PPT/Word charts & tables Risk: prose numbers still manual

How it works: Buy Macabacus single-seat. In any client deck or Word memo, embed Excel objects as named-range links instead of typing values or pasting screenshots. A single "Manage Links" refresh propagates the new model values into every linked chart and table. Continue to enforce the "model is source of truth" rule for any prose numbers (manual reconciliation).

What it catches: Chart and table drift in PowerPoint and Word — the most visible client-facing surface.

What it doesn't catch: Inline prose numbers like "2030 token revenue compresses to $1,874B" — still typed by hand. And Macabacus is built for a human at the Excel keyboard; Claude operating headless doesn't drive it.

Option C — SSOT + template render (Quarto-driven)

2-3 days build + rework Coverage: all deliverable types Risk: prose flattens; existing briefs must be redone

How it works: Build a Python orchestrator (build_brief.py model.xlsx) that reads named ranges and renders Word via docxtpl, PPT via python-pptx, HTML/MD via Jinja2. For narrative deliverables with embedded numbers, write in Quarto .qmd source files that compile to Word + HTML + PDF + PPT from one master. A Makefile (or thin Python equivalent) declares which artifacts depend on which Excel + template combinations.

What it catches: Everything — total dirty-flag tracking across all deliverable formats.

What it doesn't catch: The flattening tax on prose is real. A meaty 2,500-word brief written as Quarto template + value lookups reads more clinical than one written freehand. Existing briefs require a one-time rewrite into templated form.

Option D — Hybrid (A + B + selective C)

~1 day build + $200-360/yr Coverage: AI-built + human-Excel-built + narrative + tabular Risk: two systems but minimal overlap

How it works:

  • Build Option A's provenance layer — the AI-agent-native piece. Covers the missing 20% Claude Code doesn't ship.
  • Buy Macabacus single-seat — for the human-Excel-power-user moments where you're embedding a chart or table from a named range into a client deck or Word memo. Cheap insurance.
  • Selectively adopt Quarto for pure-numeric deliverables (tear sheets, comp tables, archetype crosswalks) — the prose-flattening tax is acceptable when the deliverable is mostly numbers and small bullets. Don't commit prose briefs to Quarto.

This satisfies the "one unified solution over patchwork" preference: the provenance layer IS the unified solution for AI-built artifacts. Macabacus is an optional speed-up for the manual-Excel moments. Quarto is a future experiment, not a commitment.

5. Recommendation

Option D (Hybrid). Specifically:

  1. Build the provenance layer first. ~1 day of focused work. Output: a provenance.json spec, a generator that reads any xlsx and emits the manifest, a PostToolUse hook that detects drift, and a citation-coherence-audit skill. Test against the BOM token model + its three downstream deliverables (validation brief, V4 memo, Marimekko spec). Verify it catches the F-column episode retrospectively.
  2. Decide on Macabacus after. The provenance layer covers AI-built work. Macabacus only adds value for chart/table embedding in PPT or Word that you drive at the Excel keyboard. If your near-term roadmap involves heavy deck-building (e.g., the L-shape Marimekko BOM-by-archetype series), it pays for itself; if it's mostly Claude-built briefs, defer.
  3. Don't commit to Quarto. Try it once on a tear-sheet or comp-table deliverable. If the prose flattening is acceptable for that artifact type, expand. Otherwise leave it.
